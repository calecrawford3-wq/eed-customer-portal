# Stage 14: Legacy billing migration, compatibility and cutover runbook
Status: DEVELOPMENT PREPARED. NO CUTOVER, IMPORT, DOMAIN CHANGE, REDIRECT, OR LIVE PAYMENT CHANGE AUTHORIZED.

## Legacy system that must stay available
The old viewer remains at https://billing.eedpower.com. Existing invoice, estimate, additional-work and comparison links are still generated by parts of the current app. Old invoice and estimate public_access_token values may authorize actions (including estimate approval), unlike new guest_payment_token values which only authorize restricted payment. Never convert a legacy approval-capable token into a payment-only guest token, or vice versa.

Known code integrations to migrate individually:
- InvoiceDetail.jsx: invoice public viewer links.
- EstimateDetail.jsx: estimate approval and comparison viewer links.
- AdditionalWorkDialog.jsx: additional work public approval links.
- syncEstimateSnapshot.ts: outgoing legacy estimate snapshot and legacy link.
- syncInvoiceSnapshot/entry.ts: outgoing legacy invoice snapshot and link.
- syncLegalDocument/entry.ts: outgoing legal document synchronization.
- createCheckoutSession/entry.ts, generateStripeCheckoutUrl/entry.ts, generatePublicCheckoutUrl/entry.ts: legacy checkout creation.
- PortalDocumentDialog.jsx and portalDocument/entry.ts: intentional compatibility links to the old viewer.
- LegacyInvoiceImportModal.jsx: manual CSV import of legacy invoices, not a full provider ledger migration.

## Phase A: Read-only discovery
- [ ] Run Settings → Payments → Audit Legacy Billing (admin-only). Record date, app checkpoint and results.
- [ ] If any category reaches the 500-record cap, obtain a complete database export and reconcile it separately. The in-app scan is only a sample.
- [ ] Inventory all old URLs from emails, QR codes, saved texts, bookmarks, outstanding estimates, pending additional work, invoices, comparison pages and signed legal documents.
- [ ] Export original invoice/estimate records, line items, tax, payments, refunds, adjustments, PDF files, and external payment identifiers. Verify retention and export permissions.
- [ ] Identify duplicates by stable original invoice number AND source ID. Resolve any number collisions before import.
- [ ] Identify missing customer links, imported PDFs, invoice balance discrepancies, paid-status conflicts and unconverted estimates.
- [ ] Record all in-flight Stripe Checkout Sessions, asynchronous bank payments, chargebacks, refunds and webhook destinations.
- [ ] Compare live billing and portal invoices to avoid double-charging a customer for the same balance.
- [ ] Identify who currently sends each legacy link and who owns the old DNS, webhook and Stripe credentials.

## Phase B: Migration preparation
- [ ] Reconcile customers by verified ID and exact unique identity. Never auto-assign money based on a fuzzy name match.
- [ ] Run CSV import only after reviewing a preview. It requires original invoice numbers, valid customer mapping, balanced amounts and no duplicates in the scanned existing invoices. At-limit scans block importing pending full reconciliation.
- [ ] Preserve original invoices, PDFs, legal signatures, public links and audit history. Never regenerate approval-capable tokens merely to make a redirect.
- [ ] Determine a tested mapping from each old viewer path to the appropriate new customer-facing action, or retain the old viewer for that path. A payment-only guest page is NOT a substitute for an estimate approval page.
- [ ] Prepare reversible per-route forwarding only after live pilot and explicit owner approval. Do not use a blanket DNS redirect.
- [ ] Validate historical paid invoices are read-only, do not initiate another charge, and retain receipts and refund records.
- [ ] Confirm any old provider sessions are handled by their original webhook and keys until settlement/reconciliation is complete.

## Phase C: Test matrix
- [ ] Old invoice link: unpaid, partial, paid, void, combined, original PDF, expired/invalid token.
- [ ] Old estimate link: sent, approved, declined, expired, required legal agreement, deposit.
- [ ] Old additional-work approval: pending, approved, declined, revised scope and expired token.
- [ ] Old comparison link: customer-specific scope and version.
- [ ] Old legal document link: signatures remain valid and preserved.
- [ ] Old Stripe Checkout link: completed, canceled, in-flight and pending ACH, refund and dispute.
- [ ] New portal invoice/estimate: no duplicate record, correct balance, owner isolation, correct legal/approval capability.
- [ ] Two separate customers, a signed-out guest and an admin. No cross-customer data.
- [ ] iPhone Safari, Android Chrome, email/SMS links and printed QR codes.
- [ ] Old and new notification templates: links point to the correct action and can be revoked where supported.
- [ ] Backup restoration and route rollback rehearsal, including already-paid but not-yet-recorded transactions.

## Phase D: Reversible cutover (requires owner approval)
1. Finish Stage 13 pilot and owner acceptance.
2. Snapshot all relevant records and confirm rollback version, operator and monitoring window.
3. Choose a small set of new, verified link types for a pilot; keep legacy link types unchanged.
4. Switch new link generation for the approved types only. Do not overwrite or invalidate historical tokens.
5. Monitor payment receipts, approvals, email links, webhook errors, customer support and duplicate invoices.
6. Expand by link type only after signed test evidence. Keep old domain and webhook endpoints available for in-flight links.
7. Decommission old endpoints only after retention, settlement, legal document and customer-bookmark obligations are met, with separate owner approval.

## Emergency rollback
- Stop issuing new migrated links, not existing webhook processing.
- Restore the last approved link-generation behavior or reversible route mapping.
- Preserve old domain, original viewer and existing signed tokens.
- Reconcile payment and approval events that occurred during the cutover before any data restoration.
- Do not roll back invoice payment data blindly or overwrite provider-confirmed receipts.
- Notify affected customers only when necessary, and retest old and new links before resuming.
